**Approach for the server side (D-05), decided at planning:** `handle_errors` is rejected for the public block for the same reason the `essai` block rejected it (deploy/caddy/essai.caddy l. 37 to 40, scripts/render-caddy.ts l. 216 to 219): all site blocks of the shared Caddy listen on the same port and the Caddyfile adapter merges them into one HTTP server; a `handle_errors` in any block adds error routes to that shared server, and Caddy 2.11.2 then logs handled errors of every site at debug level. The risk therefore applies to the public block exactly as to `essai`. The chosen way creates no error route at all: a `file` matcher selects requests whose path is neither an existing file nor an existing directory (`@introuvable not file {path} {path}/`, a trailing slash matches a directory per the Caddy matcher docs), and a `handle` block rewrites them to `/404.html` and serves it with `file_server { status 404 }` (the `status` subdirective of `file_server` is documented as « particularly useful when responding to a request with a custom error page »). This is a normal response with status 404, logged in the site's own access log like any other request; no error is raised, so no log level changes anywhere. `handle` runs before the top-level `file_server` in Caddy's directive order, so existing files and directory redirects (`/methode` to `/methode/`) are untouched. A release without `404.html` gets the same 404 with an empty body (safe fallback). `try_files` alone was rejected: it would serve `404.html` with status 200.

Réponse 404 (gzip demandé) : `Content-Encoding: gzip`, `Vary: Accept-Encoding`, `Cache-Control: no-cache`, CSP du bloc, HSTS `max-age=300`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, pas d'en-tête `Server` : mêmes en-têtes que la page d'accueil. Journal d'accès : les 404 y sont notées en `info` (« handled request », IP masquée `127.0.0.0`) ; journal du conteneur : aucune ligne `error`, seulement trois `warn` dus au Caddyfile local (admin coupé, HTTP/2 et HTTP/3 sans TLS).

Liens symboliques (dist copié avec `lien.txt -> /etc/os-release`, `casse.txt -> /nexiste`, `dossier-lien -> /etc`, `themes/lien-profond.txt`), bloc de base contre nouveau bloc : résultats **identiques** pour chaque lien valide (Caddy les suit dans les deux cas : exposition existante, fermée en amont par le refus de `activer`, CR-01). Seules différences : le lien cassé et `/nexistepas/` reçoivent la page 404 au lieu d'un corps vide. La règle n'ouvre donc aucun nouveau chemin vers un fichier. Conteneurs arrêtés (`--rm`), fichiers temporaires supprimés.

**Observation (non corrigée, à décider) :** une requête conditionnelle sur la 404 (`If-None-Match` avec son ETag, ou `If-Modified-Since`) reçoit 404 **sans corps** : `file_server` de Caddy 2.11.2 évalue les préconditions même avec `status 404`. Essai Chromium (serveur Node local reproduisant exactement ce comportement, hors dépôt) : Chromium n'envoie jamais de requête conditionnelle pour une 404, la page s'affiche à chaque visite et au rechargement. Un autre navigateur ou un cache intermédiaire qui revaliderait une 404 montrerait une page blanche avec le code 404 (le pire cas égale le comportement actuel, corps vide). Durcissement possible si Erwan le veut : `request_header -If-None-Match` et `request_header -If-Modified-Since` dans `handle @introuvable` (non essayé, hors du plan, laissé tel quel pour ne pas improviser sur le bloc du serveur).

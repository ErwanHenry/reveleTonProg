## Summary

Most of the phase holds up. The share tags cannot claim a wrong host, and the image is never requested. The site name change keeps the probe marker. The 404 page has no canonical and carries `noindex`. The CSS restructuring does what the summaries claim. Most edited tests still protect the property they protected before.

There are four real problems, in order:

1. **The Caddy 404 rule serves a blank page on a revalidation. This is proved.** In a throwaway `caddy:2.11.2-alpine` container, an `If-None-Match` or `If-Modified-Since` request on an unknown path returns `404` with a 0-byte body. A `Range` request returns `404` with a partial body and `Content-Range`. The 09.1-02 summary dismissed the conditional case because "Chromium ne revalide pas une 404". That is true for Chromium. It is false for **WebKit**: a local Playwright WebKit run sent `If-None-Match` and `If-Modified-Since` on the second visit to the same unknown URL and rendered a blank page. WebKit is the engine of every iOS browser, so the defect is reachable by ordinary visitors. Stripping the request headers inside the handle fixes it. The fix was proved on 2.11.2, and the two-header version proposed in the summary is not enough.
2. **Home page regression in « Gros caractères ».** The theme block moved out of `.lecteur`, so « Voir tous les candidats » / « Consulter la liste des candidats » lost the 48 px target. It measures 26 px in Gros caractères (21 px in normal mode). « Comment nous travaillons » stays at 44 px.
3. **« thème par thème ».** It appears in the new home presentation and in the home description. That description is now the `og:description` shown next to the share image. The phrase contradicts the reasoning written in `src/lib/partage.ts`: the site opens with one theme. This needs an owner decision.
4. **Stale revision dates.** The Mentions légales and Méthode texts changed (renamed link labels), but their `REVISION` dates did not. The footer of the legal page still shows « 10 novembre 2026 ».

No structural (fallow) findings were provided for this review.

## Critical Issues

### CR-01: Unknown path plus a conditional or range request returns 404 with an empty or truncated body (blank page in Safari and every iOS browser)

**File:** `scripts/render-caddy.ts:163-174` (rendered at `deploy/caddy/site.caddy:16-22`). Related: `tests/repo/caddy.test.ts:382-458`, `docs/RUNBOOK.md:640`, and the dismissal in `.planning/phases/09.1-.../09.1-02-SUMMARY.md:21,99`.

**Issue:** `file_server { status 404 }` still runs Go's `http.ServeContent` precondition and range logic. The override writer turns the 304, 412 or 206 status into 404 but keeps that response's body length. I reproduced the block (same `root`, `encode zstd gzip`, top-level `file_server`, `@introuvable`, `handle`, deferred `header` with `Cache-Control "no-cache"`) in a throwaway `caddy:2.11.2-alpine` container on 127.0.0.1:18093, using the real `dist/404.html` (16 063 bytes):

| Request on `/nope` | Status | Body |
|---|---|---|
| plain GET or HEAD, with or without `?x=1`, `%2e%2e` path | 404 | full 404.html |
| `If-None-Match: <etag of 404.html>` (identity, `-gzip` and `-zstd` variants) | 404 | **0 bytes** |
| `If-Modified-Since: <future date>` | 404 | **0 bytes** |
| `If-Match: "zzz"` | 404 | **0 bytes** |
| `Range: bytes=0-5` | 404 + `Content-Range: bytes 0-5/64` | **6 bytes** |

The 404 response carries `ETag`, `Last-Modified` and `Cache-Control: no-cache`, so browsers store it and revalidate it. A local Playwright run against a Node server that answers exactly like Caddy (404 with body first, then 404 with no body on a matching validator) gave:
- **WebKit:** first visit to `/nexistepas/` shows « Page introuvable ». The next visit to the same URL sends `If-None-Match: "abc"` and `If-Modified-Since`, gets an empty 404 and renders a **blank page**.
- **Chromium:** does not revalidate a 404, so the problem never shows there.

The plan's Chromium-only check therefore missed it.

Failure scenario: an iPhone visitor follows a stale link (an old theme address, or a person filtered out by 09-15) and sees the 404 page. Opening the same link again later from a message or the history shows a white page with no navigation.

The summary proposes `request_header -If-None-Match` and `-If-Modified-Since`. That is correct but **not sufficient**: `If-Match`, `If-Unmodified-Since` and `Range` (with or without `If-Range`) still produce empty or truncated 404 bodies.

**Fix (proved on 2.11.2 in a second throwaway container, 127.0.0.1:18095):** strip every precondition and range header inside the handle. Inside a `handle`, `request_header` sorts before `file_server`, so it applies before the precondition evaluation. After the change, all five requests above returned the full 16 063-byte page with code 404. Revalidation of real files (`/methode/` with its own ETag) still returned 304, because the handle does not touch them.
```ts
const LIGNES_INTROUVABLE = [
  // ...comment lines, plus one line: "préconditions et Range retirés : sinon Caddy 2.11.2 répond 404 sans corps
  // (If-None-Match, If-Modified-Since, If-Match) ou tronqué (Range), et Safari revalide une 404"
  '\t@introuvable not file {path} {path}/',
  '\thandle @introuvable {',
  '\t\trewrite * /404.html',
  '\t\trequest_header -If-*',
  '\t\trequest_header -Range',
  '\t\tfile_server {',
  '\t\t\tstatus 404',
  '\t\t}',
  '\t}',
];
```
If you prefer explicit names to the wildcard (both are accepted by 2.11.2), list `-If-None-Match`, `-If-Modified-Since`, `-If-Match`, `-If-Unmodified-Since`, `-If-Range`, `-Range`.

Then:
- update the `REGLE` array and the comment assertions in `tests/repo/caddy.test.ts`;
- regenerate `deploy/caddy/site.caddy`;
- add a RUNBOOK opening check: `e=$(curl -sI https://<domaine>/nexistepas/ | awk 'tolower($1)=="etag:"{print $2}' | tr -d '\r'); curl -s -H "If-None-Match: $e" https://<domaine>/nexistepas/ | grep -c 'Page introuvable'` must print `1`;
- correct the observation in 09.1-02-SUMMARY.

Size: small (about 6 lines of code, 2 test lines, 1 RUNBOOK line). The server block is applied only at 09-12, so the fix must land before that plan.

## Info

### IN-01: `/404.html` itself is served with code 200
**File:** `scripts/render-caddy.ts:167`. The `file` matcher finds `/404.html`, so a direct request returns 200 with the 404 content: a soft 404 for one URL. It was proved in the container. `noindex` limits the harm.
**Fix (optional):** `@introuvable` as `expression !file({'try_files': [{path}, {path}+'/']}) || {path} == '/404.html'`, or a second matcher `@erreurdirecte path /404.html` routed to the same handle.

### IN-02: check-dist accepts any bytes named `partage.png`; the `--check` fingerprint is advisory
**File:** `scripts/lib/check-dist.ts:981-988`; `scripts/partage.ts:60-114`.
- check-dist checks only the name, the location and the size. It never reads the PNG signature or the IHDR, so an HTML or SVG file renamed `partage.png` and under 100 KB passes. Risk is low: Caddy serves it as `image/png` with `nosniff`.
- The `tEXt` chunk fingerprints the filled HTML only. It does not cover the pixels or the capture parameters in `partage.ts`. Anyone can forge or keep the chunk by hand, and its CRC is not checked.

Parsing is robust: chunk lengths beyond the buffer stop the loop, and buffers shorter than 33 bytes return "pas un PNG". `tests/scripts/partage.test.ts` runs `problemesImage` on the committed file under `npm test`, which is adequate against accidental drift. The image (viewed) matches the current texts, domain and colours.
**Fix (optional):** reuse `lireDimensions` in check-dist to reject a `partage.png` that is not a 1200 x 630 PNG.

## Verified and found sound

- **Caddy directive order.** Inside the site block, `header` (deferred) runs before `handle`, which runs before the top-level `file_server`; `encode` wraps everything. Behaviour proved on 2.11.2:
  - real files: 200, ETag, 304 revalidation unchanged;
  - `/methode` gets 308 to `/methode/`;
  - HEAD on an unknown path returns 404 with the full headers;
  - a query string is ignored by the matcher;
  - percent-encoded paths are decoded before the `file` check (`/%C3%A9.txt` and `/f%2520e.txt` resolve to the real files);
  - `%2e%2e` traversal gives the 404 page;
  - the deferred header block (CSP, nosniff, `Cache-Control: no-cache`) also applies to the 404;
  - no cache rule could turn the 404 into a cached 200;
  - a release without `404.html` gets a 404 with an empty body, as the comment says.

  The `www.` block and the `essai` block are untouched (tested). No `handle_errors`. The rewrite target is fixed.
- **Symlinks (Phase 8 CR-01).** The new rule neither adds nor removes symlink following: the `file` matcher and `file_server` both follow links, which was re-observed. Protection still depends on the Phase 8 upload-side refusal.
- **Share tags.** `og:url` and `og:image` derive only from `Astro.site`, and only when `mode !== 'preview'` and not `pageErreur`. Preview, `404.html`, `essai`, `.invalid`, `http:`, a wrong path or a relative image are all refused by `PARTAGE_INCORRECT` (code read, cases in `domaine.cas.ts` / `partage.cas.ts`). The built `dist/index.html` carries `https://reveletonprog.fr/` and `https://reveletonprog.fr/partage.png`. No page references the image outside `og:image`, and `vie-privee.spec.ts` asserts that no request is made for it.

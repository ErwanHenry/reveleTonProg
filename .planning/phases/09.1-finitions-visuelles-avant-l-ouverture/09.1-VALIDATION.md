### Phase guard list (D-06), run by every plan, each command alone, in this order

1. `fnm exec --using=24 npm run check`
2. `TZ=Europe/Paris fnm exec --using=24 npm test`
3. `RTP_CONTENT_ROOT=tests/fixtures/corpus-valide fnm exec --using=24 npm run build && RTP_CONTENT_ROOT=tests/fixtures/corpus-valide fnm exec --using=24 npm run check-dist`
4. `RTP_CONTENT_ROOT=. fnm exec --using=24 npm run build -- --outDir dist-reel && RTP_CONTENT_ROOT=. fnm exec --using=24 npm run check-dist -- --dist dist-reel --mode production`
5. `RTP_CONTENT_ROOT=. RTP_MODE=preview fnm exec --using=24 npm run build -- --outDir dist-preview && RTP_CONTENT_ROOT=. fnm exec --using=24 npm run check-dist -- --dist dist-preview --mode preview`
6. `fnm exec --using=24 node scripts/render-caddy.ts --check && fnm exec --using=24 node scripts/favicon.ts --check`
7. `fnm exec --using=24 npm run e2e` (axe AA on every page and level, 320 px and 160 %, no-JS, page weight and both 4G profiles including « Slow 4G simulé » under 1 s, CSP header and meta, keyboard, privacy, bfcache, review page)

A guard is never weakened to let a change pass. A test is edited only where a plan names the edit and its reason (a copy string that changes, an explicit exception for exactly `404.html`, a LOCKED rule changed with Erwan's yes); otherwise the change is fixed or dropped.

Platform notes: never run `npm test` and `npm run e2e` at the same time in the same tree (shared `.astro` cache). Lot B runs in `../reveleTonProg-design` with its own `node_modules` and cache; avoid running two e2e suites on the machine at once (4G timings).

## Sampling Rate

- **After every task commit:** quick run of the test files the task touched; build run filtered on the task's dist modules for tasks touching `src/pages/**`, `src/components/**`, `src/layouts/**`, `src/styles/**`, `scripts/lib/check-dist.ts` or `tests/dist/**`; the e2e file of the task on the fixture.
- **After every plan:** the full guard list (lot A on `main`; lot B on the branch tip in 09.1-08 and on `main` in 09.1-09). Lot A pushes `main` once (end of 09.1-05); 09.1-01 to 09.1-04 push only the backup branch `sauvegarde/finitions-lot-a` (no CI, no deployment). Lot B pushes the branch and runs CI through a draft pull request; `main` receives lot B once (09.1-09).
- **Execution order:** 09.1-01, 09.1-02, 09.1-03, 09.1-04, 09.1-05 one at a time on `main` (they alternate with Phase 10 plans, never concurrently; 10-01 must be finished first); 09.1-06 to 09.1-08 in the worktree (may run while a Phase 10 plan uses `main`, except the docs commits of the main tree); 09.1-09 on `main`, after Erwan's answer, before 09-11.
- **Before `/gsd:verify-work`:** full guard list green on `main`, CI green, 09.1-MESURES.md row « main final » with the FIN-03 and FIN-04 verdicts, cleanup verified.
- **Max feedback latency:** 60 s (node), 8 min (e2e), one deployment cycle with Erwan's approval.

Waves: 1 = 09.1-01, 09.1-02; 2 = 09.1-03; 3 = 09.1-04; 4 = 09.1-05; 5 = 09.1-06; 6 = 09.1-07; 7 = 09.1-08; 8 = 09.1-09.

**Timing of the FIN-04 measure:** the final measure (row « main final ») is taken on `main` in 09.1-09 and the phase closes before the December import (Phase 10 plans 10-05 and 10-06, 10 to 16 December, which change `src/content/candidats/*.yaml` and the Méthode case). The measured commit is recorded; the figure is never compared with a post-import build.

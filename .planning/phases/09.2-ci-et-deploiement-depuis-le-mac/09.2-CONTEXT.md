# Phase 9.2: CI et déploiement depuis le Mac - Context

**Gathered:** 2026-11-18
**Status:** Ready for planning
**Source:** messages d'Erwan du 2026-11-18 : « Attention, je ne veux pas déployer sur GH où je n'ai plus de crédit, je veux monter une CI sur mon MAC », puis, après explication des trois voies possibles, « Script sur le Mac ».

<domain>
## Phase Boundary

Donner à Erwan deux commandes locales, lancées sur son Mac, qui remplacent pour lui le run GitHub Actions : l'une rejoue les contrôles de la CI, l'autre construit le site et l'envoie au serveur, avec les mêmes gardes que le job `deploy` de `.github/workflows/ci.yml` et une confirmation humaine à la place de l'approbation de l'Environment GitHub. Exigences : LOC-01 à LOC-04.

Hors périmètre : exécuteur GitHub auto-hébergé (écarté, dépôt public) ; suppression ou mise en sommeil des workflows GitHub (décision séparée d'Erwan, D-11) ; toute modification du serveur autre que l'ajout d'une clé publique (D-09) ; la sonde externe et les sauvegardes, qui restent où elles sont.

Fait établi le 2026-11-18, à garder dans la documentation : le dépôt est public, ses workflows tournent sur des machines standard de GitHub, et les runs du jour ont réussi ; ces minutes sont gratuites. Erwan a choisi le script local en connaissance de cause.
</domain>

<decisions>
## Implementation Decisions (orchestrateur, à partir du choix d'Erwan ; les points marqués « à confirmer » lui sont montrés avec les plans)

- **D-01 :** deux commandes npm, sans nouvelle dépendance : `npm run ci:local` (contrôles) et `npm run deploy:local` (construction, envoi, activation, vérification ; sous-commandes `etat` et `retour`). Code en TypeScript exécuté par Node 24 (`scripts/ci-local.ts`, `scripts/deploy-local.ts`, logique dans `scripts/lib/`), point d'entrée testable `executer(argv, deps)` comme `scripts/archive-source.ts`.
- **D-02, parité :** `ci:local` rejoue les étapes des jobs `verifier` et `e2e` de `ci.yml` (migrate, validate sur les deux corpus, ids.lock comparé à `origin/main`, astro check, tests, builds fictif, réel production et réel preview, check-dist de chacun, tests navigateur). Un test de dépôt compare la liste des étapes locales à celles de `ci.yml` pour qu'elles ne dérivent pas. La recherche de secrets (job `secrets`, gitleaks) est lancée si `gitleaks` est installé ; sinon l'étape est rapportée « non exécutée » en toutes lettres et bloque `deploy:local` (un déploiement sans recherche de secrets n'est pas un déploiement contrôlé). Installer gitleaks avec Homebrew est une action d'Erwan, écrite au RUNBOOK.
- **D-03, preuve de CI :** `ci:local` écrit, hors du dépôt (`~/.cache/rtp/ci/<sha>.json` ou équivalent), un reçu daté : commit complet, arbre de travail propre, résultat de chaque étape. `deploy:local` exige un reçu vert pour le commit exact, sinon il lance lui-même `ci:local`. Un reçu ne vaut que pour un arbre propre.
- **D-04, conditions d'un déploiement :** arbre de travail propre ; HEAD égal à la tête de `origin/main` après `git fetch` (rien de non poussé ne part en ligne) ; garde de gel rejouée (`scripts/garde-gel.ts`, mêmes options `--urgence` et `--justification`) ; cible `essai` ou `production` lue dans un fichier local hors dépôt (`~/.config/rtp/deploiement.env` : cible, hôte, utilisateur, URL), jamais dans le dépôt public. Classement site ou hors site par `ops/site-touche.sh` : un commit qui ne touche pas le site n'est déployé que sur demande explicite (`--forcer`).
- **D-05, cloisonnement (équivalent de WR-04) :** la build de déploiement est construite dans une copie propre du commit (worktree git temporaire, `npm ci --ignore-scripts`, `npm audit signatures`, `npm run build`, `npm run check-dist -- --mode production`, `RTP_DEPLOIEMENT` selon la cible), dans un environnement de processus qui ne contient ni la clé ni les mots de passe. L'étape d'envoi n'exécute que `rsync`, `ssh`, `curl`, `jq` et `git` : aucun code de dépendance npm ne tourne avec accès à la clé. Empreinte de l'arbre calculée après la build et revérifiée juste avant l'envoi ; refus de tout lien symbolique ou fichier spécial ; `dist/version.json` doit porter le commit.
- **D-06, confirmation humaine :** avant tout envoi, le script affiche la cible, le commit et son sujet, la version en ligne (verbe `etat`), le résumé des fichiers qui changent depuis cette version, l'empreinte, puis exige une phrase tapée au clavier (par exemple `deployer essai 1a2b3c4`). Il refuse de continuer si l'entrée standard n'est pas un terminal, et n'a aucune option du type `--oui`. C'est ce qui remplace l'approbation GitHub : un agent ne peut pas confirmer à la place d'Erwan. La cible `production` exige une phrase distincte.
- **D-07, après l'activation :** mêmes vérifications que le workflow (verbe `etat`, `/version.json` du commit, en-têtes HSTS et CSP), mot de passe de l'hôte d'essai lu dans son fichier et passé à curl par son entrée standard, jamais dans les arguments. Échec après activation : retour automatique vers la version exacte notée avant, sauf retrait d'urgence.
- **D-08 :** `deploy:local retour [<sha>]` remplace `rollback.yml`, avec la même confirmation.
- **D-09, clé (écriture serveur, accord d'Erwan requis) :** une clé ed25519 dédiée au Mac, créée localement dans `~/.config/rtp/` (jamais affichée, jamais dans le dépôt), distincte de la clé de GitHub. Sa partie publique est ajoutée à `authorized_keys` de l'utilisateur de déploiement avec la même ligne `restrict,command=…`. Cette écriture est faite par la session principale, après l'accord explicite d'Erwan, hors des plans exécutés par les sous-agents. L'empreinte du serveur reste épinglée (`~/.config/rtp/known_hosts-deploy`, jamais de scan).
- **D-10 :** chaque déploiement et chaque retour ajoute une ligne JSON à un journal local hors dépôt (date UTC, commit, cible, version précédente, résultat). Aucune donnée personnelle, aucun secret.
- **D-11 (à confirmer par Erwan, après le premier déploiement local réussi) :** les workflows GitHub ne sont pas modifiés par cette phase. Mettre le déploiement GitHub en sommeil (retirer la variable `DEPLOY_CIBLE`) ou désactiver Actions est un changement de réglage GitHub : sa décision, son accord explicite. Le verrou du serveur sérialise de toute façon deux activations concurrentes.
- **D-12 :** documentation : section du RUNBOOK « CI et déploiement depuis le Mac » (prérequis, première installation de la clé, usage, pannes, retrait d'urgence), ADR-063, README ; assertions dans `tests/repo/docs.test.ts`.
- **D-13 :** le premier déploiement réel est lancé par Erwan dans son terminal. Avant lui, une répétition à blanc (`--dry-run` : tout jusqu'à la confirmation exclue, aucun accès en écriture au serveur) est faite par l'orchestrateur.

### Claude's Discretion

</decisions>

<constraints>
- CLAUDE.md : Node 24 (`fnm exec --using=24`), aucune nouvelle dépendance npm, aucun secret dans le dépôt (public), textes français sans tiret long ni moyen.
- Sécurité : ne jamais afficher ni mettre sur une ligne de commande une clé, un mot de passe ou une URL de ping ; lire les secrets depuis `~/.config/rtp/`. Les sous-agents n'ont aucun accès `ssh` : les tests utilisent des exécutables factices (ssh, rsync, curl simulés) et un faux serveur local. Toute écriture sur le VPS passe par la session principale avec l'accord explicite d'Erwan. Le nom d'hôte, l'utilisateur et l'adresse du serveur ne vont pas dans le dépôt.
- Ne modifier ni `.github/workflows/*.yml`, ni `ops/commande-deploiement.sh`, ni le serveur : le contrat des verbes `etat`, `activer`, `retour` et du dépôt `incoming/<cible>/<sha>/` est repris tel quel.
- Ne jamais toucher `src/content/**`, `archives/**`, `data/**`.
- Tous les garde-fous existants restent verts ; `npm test` complet avant chaque push ; vérifier la CI GitHub après chaque push tant qu'elle tourne.
- La machine d'Erwan est souvent très chargée par un autre projet : prévoir des délais larges, des messages de progression, et ne jamais lancer deux `astro build` en même temps dans le même dossier.
- Sous-agents sur Opus ou Sonnet ; exécution un plan à la fois sur `main`.
- Un push qui touche le site demande un déploiement : cette phase ne touche pas le site servi (scripts, tests, docs), à vérifier avec `ops/site-touche.sh`.
</constraints>

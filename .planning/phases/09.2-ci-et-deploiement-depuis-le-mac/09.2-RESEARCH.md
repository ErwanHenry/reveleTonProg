## 2. Ce qui diffère sur ce Mac (relevé le 2026-11-18, macOS 15.7.9, arm64)

| Outil | Constat | Conséquence pour les plans |
|---|---|---|
| `rsync` | `/usr/bin/rsync` est **openrsync** (« protocol version 29, rsync version 2.6.9 compatible ») ; aucun rsync Homebrew installé (formule `rsync` 3.5.2 disponible) | voir les trois lignes suivantes |
| `--chmod=D755,F644` | **refusé** par openrsync (« invalid argument », code 1, essai local entre deux dossiers temporaires) ; `--chmod=u=rwX,go=rX` est accepté mais **ignoré** (modes 700/600 conservés) | ne jamais passer `--chmod` ; normaliser les modes dans la build (dossiers 0755, fichiers 0644) avant l'empreinte. Sans `-p`, le rsync 3.2 du serveur crée les fichiers avec le mode source masqué par son umask 022 : même résultat que `--chmod=D755,F644` |
| Commande serveur envoyée par openrsync | capturée avec un faux `ssh` : `rsync --server -r -t --dirs . essai/<sha>/` | passe les filtres de `ops/commande-deploiement.sh` (options sans barre oblique, ni `--delete`, ni `--sender`). **Non vérifiable ici :** que le `rrsync -wo -no-del -munge` du serveur (rsync 3.2.x) accepte `--dirs`. Échec possible au premier envoi réel, sans risque (rien n'est activé avant un envoi complet). Décision de l'orchestrateur (2026-11-18, révision) : **rsync 3 obligatoire pour un envoi réel** ; openrsync est refusé avec un message qui dit `brew install rsync` et `RTP_RSYNC` ; le premier envoi réel reste un point de contrôle (plan 08) |
| `bash` | 3.2.57 (`/bin/bash`) | aucune logique nouvelle en bash : tout en TypeScript ; seuls `ops/site-touche.sh` (déjà testé sur Mac) et le faux serveur des tests (`ops/commande-deploiement.sh`, déjà joué sur Mac par `tests/repo/commande-deploiement.test.ts`) passent par bash |
| `flock` | absent | verrou local par `mkdir` atomique plus fichier `pid` (verrou abandonné repris si le processus n'existe plus) ; le faux serveur remplace `flock` comme le banc existant |
| `mv -T` | `gmv` (coreutils) présent dans `/usr/local/bin` | le faux serveur l'utilise comme le banc existant ; sans `gmv`, les cas de bascule sont sautés sur Mac (la CI Linux les joue) |
| `sha256sum` / `shasum -a 256` | les deux présents (`/usr/local/bin/sha256sum` vient de coreutils et peut manquer sur un autre Mac ; `/usr/bin/shasum` est d'origine) | l'empreinte est calculée en TypeScript (`node:crypto`), au même format que `find . -type f -print0 \| LC_ALL=C sort -z \| xargs -0 -r sha256sum \| sha256sum` ; un test compare au pipeline shell joué avec `shasum -a 256` |
| `find -print0 \| sort -z \| xargs -0 -r` | BSD `sort -z` et `xargs -r` fonctionnent (essai local) ; dans les sessions de Claude Code, `find` est une fonction du shell qui appelle `bfs` | ne pas dépendre de `find` du shell dans le code ; parcours en `node:fs` (`lstat`, aucun lien suivi) |
| `gitleaks` | absent | action d'Erwan : `brew install gitleaks` (8.30.1, même version que la CI) avant le premier déploiement |
| `jq` | `/usr/bin/jq` 1.7.1 (Apple) | utilisé pour `version.json` comme la CI |
| `ssh` | OpenSSH 9.9p2, `ssh-agent`, `ssh-add`, `ssh-keygen` d'origine | agent éphémère dédié possible (voir §4) |
| `curl` | 8.7.1 | `--config -`, `--retry-all-errors` disponibles |
| `sandbox-exec` | présent (déprécié par Apple mais fonctionnel sur macOS 15.7.9) : un profil `(deny file-read* (subpath ...))` bloque bien `cat` (« Operation not permitted ») | cloisonnement de la build, refus de déployer s'il manque |
| Node | `fnm exec --using=24` donne v24.22.2 | les scripts vérifient `v24.` au départ |
| `~/.config/rtp/` | contient déjà `known_hosts-deploy`, `rtp-deploy-github.pub` (pas la clé privée de GitHub), `sonde-pass`, `essai-pass` ; pas de `deploiement.env` ni de clé du Mac ; `~/.cache/rtp` n'existe pas | clé créée par Erwan avec phrase de passe, `deploiement.env` par la session principale (plan 08) |

## 3. Points du code qui contraignent la conception

- **`version.json`** : `src/pages/version.json.ts` écrit le commit seulement si `GITHUB_SHA` compte 40 hexadécimaux, sinon `dev` ; `check-dist` refuse `dev` sous `RTP_DEPLOIEMENT=1` et compare à `GITHUB_SHA`. La build locale pose donc `GITHUB_SHA=<sha complet>` dans l'environnement de la build et de `check-dist` (aucune modification de `src/`).
- **Classement site / hors site** : `CHEMINS_HORS_SITE` n'est défini que dans l'`env` de `ci.yml` (fichier non modifiable ici). Les scripts locaux le lisent dans le texte de `ci.yml` (ligne `CHEMINS_HORS_SITE: "..."`), sans le paquet `yaml` ; un test vérifie que la valeur lue est celle de l'analyse YAML.
- **`scripts/` et `package.json` comptent comme le site** (vérifié avec `ops/site-touche.sh` : `scripts/ci-local.ts`, `scripts/lib/ci-local.ts`, `package.json` répondent `true` ; `ops/installer-serveur.sh`, `tests/**`, `docs/**`, `README.md` répondent `false`). D-01 impose `scripts/` et des commandes npm : chaque push des plans 01 à 06 demandera donc un déploiement à GitHub (si `DEPLOY_CIBLE` est posée), alors que le site construit ne change pas (aucun fichier de `src/`, `public/`, `config/`, `astro.config.mjs` touché). Le classement n'est pas modifié (ci.yml interdit) : chaque plan le dit et vérifie que `src/ public/ config/ astro.config.mjs` sont inchangés.
- **Contrat exact des scripts npm** : `tests/repo/scaffold.test.ts` (« scripts npm : contrat exact ») liste chaque script ; ajouter `ci:local` et `deploy:local` demande de le mettre à jour.
- **Une seule clé autorisée sur le serveur** : `ops/installer-serveur.sh`, étape `utilisateur`, écrit et vérifie `authorized_keys` avec **une seule ligne** restreinte (`--cle-publique` refuse plus d'une ligne, code 4 ; `cles_autorisees_conformes` exige une ligne). Ajouter la clé du Mac à côté de celle de GitHub (D-09) à la main ferait répondre `[a faire]` à chaque `--verifier`, et une future application avec la seule clé de GitHub effacerait celle du Mac en silence. Le plan 07 étend l'étape à deux clés distinctes au plus (même préfixe `restrict,command=...` sur chaque ligne), avec tests ; l'écriture sur le serveur reste un point de contrôle de la session principale (plan 08).
- **Faux serveur** : `tests/repo/commande-deploiement.test.ts` joue déjà `ops/commande-deploiement.sh` sur Mac avec `RTP_BASE` temporaire, `RTP_RRSYNC` factice, `df`, `logger`, `flock` remplacés et `gmv` pour `mv -T`. Les plans en tirent un banc réutilisable (`tests/helpers/faux-serveur.ts`) : un faux `ssh` (dans un PATH de test) qui pose `SSH_ORIGINAL_COMMAND` et lance la vraie commande forcée, un faux `rsync` qui copie l'arbre dans `incoming/<cible>/<sha>/` après être passé par le filtre de la commande forcée, un faux `curl` qui sert le `version.json` de `current` et des en-têtes réglables.
- **Point d'entrée testable** : `scripts/archive-source.ts` exporte `executer(argv, deps)`, lève `Sortie(code, message)`, et ne lance `main` que si `import.meta.main`. Même forme ici.

## 4. Risques établis par la lecture, et parades retenues (révisées le 2026-11-18 après la vérification des plans)

1. **Même utilisateur Unix pour la build et la clé (D-05).** Un code de dépendance lancé par la build tourne sous l'utilisateur d'Erwan. Parades (plans 02 et 06) : profil `sandbox-exec` avec `(deny file-write*)` et liste blanche (worktree temporaire, `.git/worktrees/<nom>`, TMPDIR, cache npm), lecture refusée pour chaque chemin de la configuration (clé, `.pub`, known_hosts, mot de passe de fumée, `deploiement.env`, où qu'ils soient), `~/.config/rtp`, `~/.ssh`, `~/.config/gh` ; refus si l'un d'eux est sous le worktree ; environnement en liste blanche ; instantané (empreintes de `.git/config`, de `.git/hooks`, des fichiers de configuration et des exécutables d'envoi résolus en chemins absolus avant la build) comparé après la build et après la confirmation ; agent SSH démarré seulement après la build. Le bac à sable peut être refusé quand l'exécuteur tourne lui-même dans un bac à sable : sonde au plan 02, tests alors lancés par la session principale (jamais affaiblis).
2. **Un agent peut contourner la confirmation.** Un pseudo-terminal (`script`, `expect`) ou un appel direct de la bibliothèque passe toute vérification faite dans le processus. Décision de l'orchestrateur : la clé du Mac est créée **avec phrase de passe, par Erwan dans son terminal** ; une clé non chiffrée est refusée (code 3) par toute sous-commande qui contacte le serveur, `etat` compris (détection par `ssh-keygen -y -P ''`, sortie jetée) ; la phrase de passe est tapée à l'invite de `ssh-add` (`SSH_ASKPASS_REQUIRE=never`). La phrase de confirmation est lue sur `/dev/tty`, la CLI n'accepte aucune dépendance injectée pour elle, l'entrée standard non terminal est refusée en premier ; elle protège contre l'erreur, pas contre un attaquant (ADR-063). La répétition à blanc ne contacte jamais le serveur ; le premier `etat` réel est fait par Erwan.
3. **openrsync et rrsync** (§2) : rsync 3 obligatoire pour un envoi réel.
4. **Pushes de la phase classés « site »** (§3) : demandes de déploiement GitHub à rejeter ou approuver par Erwan, site construit inchangé.
5. **Reçu de CI falsifiable** : risque accepté ; il n'autorise rien, la barrière est la phrase de passe.
6. **Identifiants du serveur dans les journaux** : les sorties de ssh, rsync et curl passent par un masque (`<hôte>`, `<utilisateur>`, `<url>`) avant affichage et journal (plans 03 à 06).

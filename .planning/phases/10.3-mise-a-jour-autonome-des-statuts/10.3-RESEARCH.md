## Summary

La chaîne manuelle actuelle (RUNBOOK « Veille des candidatures » puis « Import de décembre ») compte quatre gestes d'Erwan : décision `decider`, `preparer` et relecture, liste blanche des thèmes, `ci:local` puis `deploy:local` avec phrase de passe. Tout le code nécessaire à chaque maillon existe déjà et est testé : détection (`scripts/lib/veille/lancer.ts`), classement (`classer.ts`), import et répétition à blanc (`scripts/import-datagouv.ts`), branche et mises à jour mécaniques (`preparer.ts`), relecture (`scripts/lib/relecture/commandes/marquer.ts`), CI locale (`scripts/ci-local.ts`, reçu par commit), build scellée, envoi, activation, test de fumée et retour automatique (`scripts/lib/deploiement/deployer.ts`), commande forcée serveur (`ops/commande-deploiement.sh`). La phase 10.3 n'invente pas de maillon : elle supprime les quatre points d'entrée humains en les remplaçant par des règles fixes, deux agents d'IA sans outil dont la sortie est contrainte et vérifiée par du code, une clé de déploiement restreinte, et une machine d'états persistante qui arrête tout au moindre doute.

Trois constats de la recherche changent le plan. (1) Le retour automatique exige que la clé automatique puisse appeler le verbe `retour` : « pas de `retour` manuel » doit se lire « `retour` limité à la version immédiatement précédente ». (2) Un commit poussé par fusion de pull request change de SHA (fusion, squash, rebase) alors que le reçu de `ci:local` et la garde « HEAD égal à `origin/main` » de `deploy:local` sont attachés au SHA : la voie sans second `ci:local` de 22 minutes est le push direct en avance rapide du commit testé sur `main` (non protégée, auto-merge désactivé, vérifié). (3) Le meilleur rempart contre l'injection de prompt n'est pas un filtre mais une conception : l'agent n'a aucun outil, ne reçoit que du texte récupéré par notre code, ne renvoie qu'un verdict, une citation et une date, la citation doit être retrouvée mot pour mot dans le texte récupéré, et seul le code écrit les fichiers, avec des gabarits fixes.

Le jeu de règles d'identité proposé (D-02) a été rejoué sur les 61 lignes réelles de `correspondances.yaml` : 59 conformes, 1 refus d'ambiguïté résolu par une règle de départage (de Villepin), 1 écart qui est une décision manuelle d'Erwan (nom de tri de Lagarde). La déduction du type de source donne 60 conformes sur 61 (le seul écart est un choix manuel plus favorable que le défaut `presse`).

**Primary recommendation :** ajouter une sous-commande `veille auto` (mode « à blanc » par défaut, « publier » après activation explicite) qui travaille dans un worktree dédié, écrit uniquement par du code (agents sans outil, sorties validées), pousse en avance rapide le commit déjà couvert par un reçu `ci:local` complet, déploie par un point d'entrée distinct `deploy:auto` avec clé directe et `--auto` côté serveur, et s'arrête avec une alerte à code fixe au moindre écart.

## Réponses aux 8 points ouverts

### 1. Restriction de la clé automatique côté serveur : option dédiée `--auto`

**Recommandation : un second argument fixe dans la ligne `authorized_keys` de la clé automatique : `restrict,command="/usr/local/sbin/rtp-deploy-command --auto"`.** `[ASSUMED]` (comportement standard de `command=` dans sshd(8) : le client ne peut écrire que dans `SSH_ORIGINAL_COMMAND`, jamais dans les arguments du `command=` ; à confirmer par la lecture de `man sshd` au plan 02).

Lu dans `ops/commande-deploiement.sh` : le script ne lit aucun argument, seulement `SSH_ORIGINAL_COMMAND` (filtre de caractères `RE_COMMANDE`, découpage en jetons, `case "${t[0]}"` sur `rsync`, `activer`, `retour`, `etat`). Ajouter `AUTO=0 ; [ "${1:-}" = "--auto" ] && AUTO=1` (tout autre premier argument : refus 64) et, quand `AUTO=1`, trois restrictions appliquées aux jetons déjà contrôlés :

| Verbe | Mode normal (inchangé) | Mode `--auto` |
|---|---|---|
| `rsync` (envoi) | `RE_DEST='^(essai\|production)/<sha>/?$'` | destination `production/<sha>/` seulement |
| `activer <cible> <sha>` | essai ou production | `production` seulement |
| `etat <cible>` | essai ou production | `production` seulement |
| `retour <cible> [<sha>]` | n'importe quelle version rangée | `production` seulement, et soit sans sha, soit sha égal à `PRECEDENT` (version immédiatement précédente de l'historique) ; sinon refus 64 |

Pourquoi `retour` n'est pas supprimé : le critère SC-3 exige le retour automatique, et `retourAutomatique()` (`deployer.ts`) appelle `retour <cible> <courantAvant>`. Après une activation, `courantAvant` est exactement `PRECEDENT` côté serveur (`trouver_precedent` lit `.historique`), donc la restriction « sha = précédente » ne gêne pas le retour automatique et interdit à la clé de remettre en ligne une version choisie plus ancienne.

Le journal (`logger -t rtp-deploy`) gagne un champ `"auto":true|false` pour distinguer sur le serveur les usages de la clé automatique.

**Piège majeur (ordre d'installation).** L'ancien script ignore `$1`. Une ligne `--auto` écrite AVANT la mise à jour du script installé donnerait à la clé automatique tous les droits de la clé manuelle. Trois garde-fous à livrer ensemble :
1. `ops/installer-serveur.sh` écrit la ligne de la clé automatique seulement si le script installé en `/usr/local/sbin/rtp-deploy-command` contient un marqueur de capacité (par exemple une ligne `# rtp-capacite: auto-v1`) ; sinon échec (code 4).
2. Preuve de restriction à chaque passage : avant tout envoi, `deploy:auto` envoie un verbe interdit pour ce mode (`etat essai`) et exige le code 64 ; tout autre code : arrêt et alerte « serveur non restreint ».
3. Test de documentation : la procédure du RUNBOOK met la mise à jour du script avant la ligne de clé.

**Installateur.** `ops/installer-serveur.sh` accepte aujourd'hui une ou deux lignes (`--cle-publique`, trois refusées, `PREFIXE_CLE` unique, `cles_autorisees_conformes` : 1 à 2 lignes). Ajouter une option `--cle-publique-auto <fichier>` (une seule ligne `ssh-ed25519`, clé distincte des deux autres) qui ajoute une 3e ligne avec le préfixe `--auto` ; `cles_autorisees_conformes` accepte 1 à 3 lignes dont au plus une au préfixe `--auto` ; la procédure de retrait (point 4 du RUNBOOK « Autoriser la clé sur le serveur » : réappliquer sans la clé) reste la même forme : réappliquer l'étape `utilisateur` sans `--cle-publique-auto`. Tests : `tests/repo/installer-serveur.test.ts` et `tests/repo/commande-deploiement.test.ts` (cas `--auto` : chaque verbe autorisé, chaque verbe refusé, `retour` avec une autre version que la précédente refusé, argument inconnu refusé).

### 2. Branche et historique : push direct en avance rapide sur `main`

**Recommandation : commit local sur une branche de travail du worktree dédié, `ci:local` complet sur ce commit, puis `git push origin <sha>:refs/heads/main` sans `--force` (refusé par git si `main` a avancé).** Pas de pull request.

Faits vérifiés (lecture seule) :
- `main` n'est pas protégée : `gh api .../branches/main/protection` répond 404 « Branch not protected » ; `gh api .../rulesets` répond `[]` `[VERIFIED: gh api, 2026-11-26]`.
- `allow_auto_merge: false`, fusions merge, squash et rebase permises `[VERIFIED: gh api]` : une PR fusionnée automatiquement demanderait de changer un réglage GitHub (interdit à cette session) ou d'attendre une fusion immédiate par API.
- Une fusion (merge, squash, rebase) crée un nouveau SHA. Le reçu de `ci:local` (`~/.cache/rtp/ci/<sha>.json`) et la garde de `deploy` (« HEAD égal à `origin/main` » puis reçu pour ce commit exact, `gardes.ts`, `deployer.ts` étapes 3 et 4) sont attachés au SHA : la voie PR coûterait un second `ci:local` complet. Durée du dernier reçu : `test` 775 s, `e2e` 392 s, total proche de 22 minutes `[VERIFIED: reçu ~/.cache/rtp/ci/c99094d4….json]`.
- Le push de `main` déclenche seulement la CI de vérification de `ci.yml` (le déploiement GitHub est en sommeil depuis le retrait de `DEPLOY_CIBLE`, RUNBOOK « Coexistence avec GitHub ») `[CITED: docs/RUNBOOK.md]` : elle sert de contrôle a posteriori, comme demandé.

Jeton de push : le dépôt est cloné en HTTPS et `gh auth status` montre un jeton OAuth du trousseau aux portées `repo`, `workflow`, `admin:public_key`, `gist`, `write:packages`, `read:org`. Trop large pour un robot, et jamais éprouvé sous launchd (la veille ne fait que des `git fetch` d'un dépôt public, sans authentification). Recommandation : une clé de déploiement GitHub en écriture, limitée à ce dépôt, ou un jeton à granularité fine `contents: write` sur ce seul dépôt, rangé dans `~/.config/rtp/` (0600), utilisé par `GIT_SSH_COMMAND` (clé) ou un `git -c credential.helper=` éphémère. Sa création est une action GitHub : à faire par la session principale avec l'accord d'Erwan, hors de cette session. Le code reçoit le moyen de pousser par injection (le test utilise un dépôt nu local), et le mode « à blanc » ne pousse rien.

Identité de commit : `git -c user.name=… -c user.email=…` explicites (les tests git doivent fixer leur identité locale, mémoire du projet) ; message de commit avec les comptes et le SHA256 court du jeu, sans nom de personne.

Divergence : si `git push` est refusé (non avance rapide), abandon de ce passage, état `main_a_avance`, nouvelle tentative au passage suivant (idempotente : tout est recalculé depuis les octets amont gardés). Pas de rebase automatique en boucle : un rebase change le SHA et refait 22 minutes de `ci:local`. Au plus une reprise dans le même passage si `main` n'a avancé que sur des chemins hors site (même classement que `ops/site-touche.sh`) ; sinon attendre le passage suivant.

Garde « seuls nos changements partent » (nouvelle, importante) : avant d'ajouter le commit, comparer la version en ligne (verbe `etat production`) et `origin/main` avec `siteTouche()` : si `main` contient déjà des changements du site non déployés (code d'une autre session mergé mais pas encore déployé par Erwan), l'automate refuse (« main contient des changements du site non déployés ») au lieu de les publier avec les données.

### 3. Agent headless : `claude -p` sans outil, sortie contrainte, jeton OAuth long

Version locale : `/usr/local/bin/claude` est la 2.1.105 `[VERIFIED: claude --version]`. L'alias de l'interpréteur (`~/.claude/local/claude`) est cassé (« native binary not installed »). Sous launchd le PATH est minimal : le chemin du binaire doit être absolu et configuré (`RTP_CLAUDE=/usr/local/bin/claude`), vérifié à l'installation par `--version`. La documentation consultée est plus récente que 2.1.105 (certains drapeaux comme `--max-turns` n'apparaissent pas dans l'aide locale) : la sonde d'installation du point de contrôle humain doit valider chaque drapeau utilisé.

Drapeaux retenus, tous présents dans l'aide 2.1.105 `[VERIFIED: claude --help]` : `-p`, `--output-format json`, `--json-schema <schéma>`, `--model sonnet`, `--tools ""` (désactive tous les outils intégrés), `--no-session-persistence`, `--permission-mode dontAsk`, `--max-budget-usd <n>`, `--disable-slash-commands`, `--strict-mcp-config` sans `--mcp-config` (aucun serveur MCP). Le prompt passe sur l'entrée standard (plafond 10 Mo `[CITED: code.claude.com/docs/en/headless]`), jamais en argument (`ps`). Avec `--tools ""` l'agent ne peut ni lire un fichier ni lancer une commande ni sortir sur le réseau : une injection dans le texte d'une source n'a aucun levier d'action, seulement celui d'un mauvais verdict. Pas besoin de `--max-turns` (un seul tour sans outil).

Authentification sous launchd, deux voies, un seul code :
- **Jeton long d'abonnement (recommandé)** : `claude setup-token` (tapé par Erwan une fois) produit un jeton OAuth d'un an, qui n'autorise que des requêtes de modèle ; il est lu depuis `~/.config/rtp/agent-claude.env` (clé `CLAUDE_CODE_OAUTH_TOKEN`, mode 0600, lecteur strict comme `lireConfig`) et passé par l'environnement du seul processus `claude` `[CITED: code.claude.com/docs/en/authentication]`. `--bare` ne lit PAS ce jeton `[CITED]` : sans `--bare`, `claude -p` charge hooks, CLAUDE.md et skills de `~/.claude` (hooks et instructions personnelles d'Erwan) : à isoler par `CLAUDE_CONFIG_DIR=~/.cache/rtp/agent/config` (dossier vide, 0700) et un `cwd` vide. L'effet réel de cette isolation avec le jeton d'environnement est `[ASSUMED]` : la précédence documentée met `CLAUDE_CODE_OAUTH_TOKEN` avant les identifiants de `/login`, ce qui suggère qu'aucun trousseau n'est lu, à prouver par la sonde.
- **Clé d'API Console (variante)** : `ANTHROPIC_API_KEY` avec `--bare` (mode recommandé pour les scripts, isole tout) et plafond `--max-budget-usd` ; facturation à l'usage. À réserver au cas où Erwan préfère un plafond de dépense dur.

Coût et délai : une vérification = un texte de source tronqué (30 000 caractères, environ 8 000 jetons) plus un court prompt : de l'ordre de quelques centimes avec Sonnet `[ASSUMED : à mesurer par la sonde, `total_cost_usd` est dans la sortie JSON]`. Par personne : 2 agents (vérification, revérification) pour le statut, 2 pour la case si elle est nouvelle. Garde de volume de l'automate : au plus 6 personnes par passage (au-delà : arrêt « volume anormal » + alerte, décision d'Erwan), délai de 5 minutes par appel (`Lanceur.delaiMs`), plafond `--max-budget-usd 0.50` par appel.

Hors ligne (coupures observées : la veille du 25 au 26 novembre journalise `Could not resolve host github.com`) : tout appel réseau avant le push échoue sans effet ; le passage s'arrête en état `hors_ligne`, aucune alerte Telegram possible (notification macOS seulement), repris au passage suivant ; après le push et avant le déploiement, l'état `pousse_non_deploye` est persisté et le déploiement est repris seul au passage suivant. Les alertes non envoyées sont gardées dans une boîte d'envoi de l'état et renvoyées au passage suivant.

Sortie : `--output-format json` renvoie un objet avec `result` et, avec `--json-schema`, `structured_output` `[CITED]` ; absent si la sortie n'est pas valide. Le code accepte `structured_output` (objet) puis, à défaut, un `result` qui se lit en JSON, et dans tous les cas revalide la forme avec son propre contrôle (jamais de confiance dans le schéma seul : « `format` n'est qu'une annotation »).

Contrat de sortie d'un agent (le même schéma pour les deux agents) :

```json
{ "verdict": "confirme | infirme | insuffisant",
  "citation": "<=300 caracteres, extrait verbatim du texte fourni",
  "date_page": "AAAA-MM-JJ | null" }
```

Le code accepte « confirme » seulement si : la citation (normalisée : NFC, espaces réduits, apostrophes unifiées, minuscules) est une sous-chaîne du texte récupéré normalisé ; la citation ne contient aucun mot interdit sans être elle-même dans la source (elle l'est par construction) ; les deux agents disent « confirme ». Tout autre cas : doute, rien n'est publié. Le second agent reçoit les mêmes entrées avec une consigne de recherche de contre-preuve (cadrage adverse), sans voir la réponse du premier.

Testabilité sans API : `Lanceur` injecté (les tests passent un faux), plus un exécutable factice `tests/helpers/faux-claude.ts` (script `sh` écrit dans un dossier temporaire, scénario lu dans un fichier, journal des arguments sans l'entrée standard) désigné par `RTP_CLAUDE`. Les tests vérifient les drapeaux exacts (`--tools ""`, pas de `--bare` avec jeton, `--no-session-persistence`), l'environnement transmis (le seul secret est le jeton, aucune autre variable), le délai, les réponses malformées, le verdict « insuffisant », la citation absente du texte, le désaccord. Un test statique interdit tout autre point d'appel de `claude`.

### 4. Règles de dérivation de l'identité (D-02)

Entrée : ligne amont `{ id, nom, ... }` (`nom` = « Prénom(s) Nom », `id` = identifiant amont, en pratique le nom de famille sans accent ni particule en minuscule : `melenchon`, `villepin`, `le-maire`, `lucas-lundy`). Prototype rejoué sur les 61 lignes réelles de `data/import/correspondances.yaml` et `data/import/2027etmoi-candidats-2026-11-01-332914fc603e.json` `[VERIFIED: exécution locale]` : **59 conformes sur 61**.

Règles :
1. Découper `nom` en mots (espaces). Chercher les découpages k (1 <= k < n) tels que le slug de `mots[k:]`, ou ce slug sans ses particules minuscules de tête, égale l'identifiant amont. Slug : NFD sans marques, minuscules, apostrophes et séparateurs vers `-`.
2. Exactement un découpage : prénom = `mots[:k]`, nom = `mots[k:]`, accents et casse du jeu conservés (Ségolène, Édouard, Maréchal).
3. Particules minuscules (`de`, `du`, `des`, `d'`, `von`, `van`, `der`, `den`, `ben`, `el`, `al`) : conservées dans `nom` (« de Villepin »), retirées de `nom_tri` (« Villepin »). Particules en majuscule initiale (« Le Maire », « Le Pen ») : conservées partout. Si deux découpages ne diffèrent que par une particule minuscule de tête (cas de Villepin : 2 découpages), départage : celui qui garde la particule dans `nom`.
4. `id` de fiche = slug(prénom + espace + nom) ; il doit respecter `ID_CANDIDAT` (`^[a-z][a-z0-9]*(-[a-z0-9]+)+$`, 80 caractères au plus) et ne coïncider avec aucun identifiant de `correspondances.yaml` (`ids` de `lireCorrespondances`), de `ids.lock`, ni de fiche existante.
5. `type_source_statut` : voir point 5. `motif` : `non_candidat` seulement si le statut amont est `renonce` et que la personne n'a jamais eu de statut (D-02) ; sinon pas de motif.
6. ### 6. Cohabitation avec la veille : sous-commande `veille auto`, lanceur commun

Recommandation : `veille lancer` reste la détection pure (rapide, alerte comptes). `veille auto` est une sous-commande de plus (`SOUS_COMMANDES_VEILLE`), lancée par le même agent launchd à la suite : `lanceur()` (`launchd.ts`) exécute `lancer` puis `auto` (aujourd'hui `exec … lancer`). Raisons : un seul plist et un seul endroit pour tout arrêter ; `auto` réutilise `etat.derniereEmpreinte` et `etat.dernierAmont` (octets gardés, SHA-256 revérifié comme `preparer`) sans second téléchargement ; une panne de `lancer` (réseau) ne doit pas empêcher `auto` de reprendre un `pousse_non_deploye` ; un passage `auto` long (30 à 40 minutes) ne retarde pas la détection puisqu'il vient après.

Worktree dédié `~/.cache/rtp/veille/auto` (distinct de `arbre`, qui reste détaché sur `origin/main`) ; `npm ci --ignore-scripts` dans les deux (le `npm ci` actuel de la veille lance les scripts de dépendances sous l'utilisateur, alors que la clé sera sur le disque ; `construire.ts` prouve déjà que le build fonctionne avec `--ignore-scripts`).

Mode par défaut « à blanc » (tout jusqu'au commit local, jamais de push ni de déploiement) tant que le marqueur d'activation `~/.config/rtp/auto-actif` n'existe pas (créé par Erwan ou la session principale après les passages d'observation). Interrupteur d'arrêt : fichier `~/.cache/rtp/veille/auto-desactive` testé en premier à chaque passage.

### 8. Masquage de l'écran de `deploy:local` : cause et correction

Cause exacte `[VERIFIED: exécution de masquer avec utilisateur « deploy »]` : `scripts/lib/deploiement/masque.ts`, `masquerConfig`, ajoute pour l'utilisateur la forme « mot entier » `(?<![A-Za-z0-9_])deploy(?![A-Za-z0-9_])`. Les caractères `:`, `-`, `.` ne sont pas des caractères de mot : `deploy:local`, `deploy-local.ts`, `deploy-production`, `deploy.ts` sont donc masqués (`npm run <utilisateur>:local`, `scripts/<utilisateur>-local.ts`). Le nom d'utilisateur du serveur est `deploy` (documenté dans le dépôt public : `ops/installer-serveur.sh`, en-tête de `commande-deploiement.sh`), donc le masque s'applique par erreur à des noms de commandes.

Correction : étendre les bornes de la forme « mot entier » pour qu'un identifiant collé à un autre mot par `:`, `-`, `.` ou `/` ne soit pas masqué. Forme recommandée, essayée sur les cas ci-dessous (tous conformes) : `(?<![A-Za-z0-9_/.:-])deploy(?![A-Za-z0-9_]|[:.-][A-Za-z0-9_])`. Les cas qui doivent continuer à être masqués : `deploy@hôte`, `compte deploy refusé`, `utilisateur deploy.` (point final suivi d'une espace ou de la fin), `(deploy)`, `deploy: Permission denied`. Les cas qui ne doivent plus l'être : `deploy:local`, `deploy-local.ts`, `scripts/deploy-local.ts`, `deploy.ts`. Le test existant (`tests/deploiement/config.test.ts`, `describe('masquer')`, lignes 249 à 276) reste la base ; ajouter les cas ci-dessus et un test qui passe tout le texte `USAGE` de `deploy-local.ts` et les messages « lancer fnm exec --using=24 npm run deploy:local » par `masquer` avec l'utilisateur `deploy` et exige qu'ils soient inchangés. À confirmer en exécutant la suite complète des tests de masquage (cas 266 : `xdeploy-facticex` doit rester inchangé).

### Pattern 1 : l'agent est une fonction pure de ses entrées

**What:** `verifier(entrees) -> { verdict, citation, date_page }` ; le code récupère les textes, appelle deux fois, vérifie la citation, décide ; l'agent n'écrit rien. **When to use:** toute vérification de statut ou de case. **Example :**

```typescript
// Source: conception de cette recherche ; drapeaux : claude --help 2.1.105
const args = ['-p', '--output-format', 'json', '--json-schema', JSON.stringify(SCHEMA_VERDICT),
  '--model', 'sonnet', '--tools', '', '--no-session-persistence',
  '--permission-mode', 'dontAsk', '--disable-slash-commands', '--strict-mcp-config'];
const r = await lancer({ commande: cfg.claude, args, cwd: dossierVide, env: envAgent(cfg),
  entree: promptAvecDonneesDelimitees, delaiMs: 5 * 60_000, libelle: 'agent de relecture' });
```

### Pattern 2 : écriture par gabarit, jamais par texte d'agent

Les cellules de `data/couverture-themes.yaml` ont un champ `note` libre dans les lignes existantes ; pour une ligne écrite par l'automate, `note` est un gabarit fixe (« aucune source de programme lue au AAAA-MM-JJ : voir urls_consultees »), `urls_consultees` ne contient que des URL nues récupérées par le code, `acces: aucun_site` et dix cellules `niveau: aucun` (seule combinaison que `lireCouverture` accepte pour `aucun_site`, et que le test `10 cellules complètes, avec une note` accepte). La case de thème est `etat: programme_non_publie`, `verifie_le` = date du jour de Paris, `verifie_par: l'agent d'IA Claude` (forme du pilote existant).

### Pattern 3 : garde de périmètre d'écriture avant tout commit

Sur le diff indexé : liste blanche de chemins (`data/import/**`, `data/dataset-datagouv.yaml`, `data/couverture-themes.yaml`, `src/content/candidats/**`, `src/content/couverture/**`, `relecture/**` si le registre y écrit, `ids.lock`, `LICENSE`) ; refus de tout changement de `texte_source`, de `archives/**`, de `src/content/mesures/**`, de `src/content/sources/**` ; `correspondances.yaml` en ajout pur ; refus de tout tiret long ou moyen et de tout mot de `regles/mots-interdits.yaml` dans les lignes ajoutées. Ce test est le filet : même un bug de l'orchestrateur ne peut pas publier hors périmètre.

### Anti-Patterns to Avoid

- **Donner un outil à l'agent** (`Read`, `Bash`, `WebFetch`) : crée un levier pour l'injection de prompt venue du jeu ou des pages ; l'agent n'en a pas besoin.
- **Écrire dans un fichier un texte produit par l'agent** (note, citation, nom) : seul le code écrit, avec des gabarits ; la citation ne sert qu'à la vérification et au rapport local.
- **Passer par `deploy:local` avec un faux terminal** : contredit ADR-063 et son avertissement ; `deploy:auto` est un point d'entrée distinct qui laisse `deploy:local` strictement inchangé (la phrase de passe reste sa barrière).
- **Réutiliser `ouvrirAgent`** : il refuse une clé sans phrase de passe (code 3, `cleChiffree`) ; pour la clé automatique on n'utilise aucun agent ssh : `-i <clé> -o IdentitiesOnly=yes -o IdentityAgent=none`.
- **Fusionner une PR pour publier** : change le SHA, invalide le reçu.
- **Rebaser en boucle** : chaque rebase relance 22 minutes de contrôles.

## Common Pitfalls

### Pitfall 1 : l'ancien script serveur ignore `--auto`
**What goes wrong:** la ligne `command="… --auto"` donne tous les droits tant que le script installé n'est pas à jour. **How to avoid:** marqueur de capacité vérifié par l'installateur, sonde de restriction (`etat essai` doit répondre 64) à chaque passage, test de documentation de l'ordre. **Warning signs:** la sonde répond 0.

### Pitfall 2 : le reçu de `ci:local` ne suit pas le SHA après rebase ou fusion
**What goes wrong:** `deploy` refuse (« aucun reçu pour ce commit exact ») ou, pire, un contournement du reçu. **How to avoid:** pousser le SHA exact testé, jamais de rebase après `ci:local` ; abandon et reprise sur divergence.

### Pitfall 3 : la sortie (renonce) d'une personne exige de retirer sa ligne de couverture
**What goes wrong:** `tests/corpus/couverture-themes.test.ts` exige « exactement une ligne par candidat du périmètre » (preview : statut le plus récent, même brouillon) : dès que l'import pose un `renonce` brouillon, la ligne de `data/couverture-themes.yaml` doit disparaître, sinon `npm test` (donc `ci:local`) est rouge. Les cases des fichiers `src/content/couverture/<thème>.yaml` restent (avertissement `PILOTE_HORS_PERIMETRE` seulement). **How to avoid:** l'écriture automatique supprime la ligne du sortant (ligne entière, parseur à texte) et la ré-ajoute à un retour dans le périmètre (retour : `renonce` vers `declare`) ; ordre `nom_tri` en collation française pour toute insertion.

### Pitfall 4 : `marquer statut` refuse `pressenti`, une date au mois, une case manquante
**What goes wrong:** refus de `marquer` (codes de sortie 1) : `pressenti` sans `--hors-perimetre` ; « un statut relu exige une date complète » (date `AAAA-MM`) ; `EQUITE_CANDIDAT_MANQUANT` si la case n'existe pas avant le statut relu sur un thème publié. **How to avoid:** décider le drapeau par `codeDansPerimetre(code)` (pas par `startsWith('renonce')`), arrêter sur `date_au_mois` avant d'appeler les agents, écrire les cases avant `marquer`.

### Pitfall 5 : textes qui annoncent un compte, écrits en dur
**What goes wrong:** `README.md` (« 61 personnalités », « 61 candidats importés ») et `docs/COUVERTURE-THEMES.md` (« 38 candidats ») contiennent des comptes que la liste de contrôle d'import (point 8) fait tenir à jour à la main ; aucun test ne les contrôle `[CITED: RUNBOOK]`. Une automatisation ne peut pas les tenir à jour sans écrire du texte libre. **How to avoid:** reformuler le README sans nombre (le site ne contient rien en dur, demande d'Erwan) ; `COUVERTURE-THEMES.md` est un rapport daté (« Mesure du 2026-11-03 sur 38 candidats »), à laisser tel quel et à marquer comme tel.

### Pitfall 6 : `ci:local` dure environ 22 minutes et partage son verrou avec Erwan
**What goes wrong:** passage launchd de 30 à 40 minutes qui bloque un `ci:local` manuel d'Erwan (code 2) ou l'inverse. **How to avoid:** report silencieux au passage suivant, alerte après trois reports ; démarrer le passage en regardant le verrou avant tout travail coûteux.

### Pitfall 7 : le gel d'import de décembre n'est pas dans `deploy:local`
**What goes wrong:** `deploy:local` ne connaît que les fenêtres des scrutins (`evaluerGel`) ; `GEL_IMPORT` (13 décembre 2026 18:00 au 15 décembre 23:59) n'est testé que par `preparer`. **How to avoid:** `deploy:auto` teste les deux juste avant `activer`.

### Pitfall 8 : la procédure manuelle d'import de décembre coexiste avec l'automate
**What goes wrong:** le RUNBOOK dit « Aucun agent n'écrit jamais une entrée sur une personne » (décision du 2026-11-13, remplacée en partie par D-02 et la délégation du 2026-11-24) et prévoit une branche `import/statuts-2026-12` poussée par Erwan du 10 au 13 décembre. L'automate pourrait pousser en parallèle et provoquer « main a avancé, recréer la branche ». **How to avoid:** question ouverte 1 ; recommandation : fenêtre de retenue de l'automate du 10 décembre 2026 au 15 décembre 23:59 (`GEL_AUTO` plus large que `GEL_IMPORT`), et mise à jour du RUNBOOK (phrase de la règle) gardée par test.

### Pitfall 9 : sortie JSON de `claude` différente selon la version
**What goes wrong:** `structured_output` absent de la 2.1.105, présent dans les versions récentes. **How to avoid:** double lecture (objet structuré, sinon `result` lu en JSON), revalidation stricte, sonde d'installation qui imprime la forme reçue (sans le prompt).

1. **Import de décembre (10 au 13 décembre 2026) : l'automate se retient-il ?**

3. **Sémantique de `acces: aucun_site` pour une personne qui a un site sans programme** : recommandation : toute ligne écrite par l'automate est `aucun_site` + dix `aucun` (forme valide la plus simple) ; si le code trouve un lien `programme` dans `liens` du jeu amont, ou si l'agent dit « programme trouvé », c'est un cas réservé (`doute_agent` ou `source_inaccessible`), pas une case `programme_non_publie`.
4. **Motif d'un désistement d'une personne connue sans motif** : non couvert par D-02 ; recommandation : cas réservé (alerte), jamais deviné.
5. **Authentification de l'agent : abonnement (jeton `setup-token`) ou clé d'API Console ?** Recommandation : jeton ; Erwan choisit (il lui faut un compte Console pour l'autre voie).
6. **Moyen de push** : clé de déploiement GitHub ou jeton à granularité fine, à créer par la session principale avec l'accord d'Erwan.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Vol de la clé automatique sans phrase de passe (lecture du fichier par un processus du même utilisateur, dépendance npm de `ci:local` ou de `npm ci`) : publication de contenu arbitraire en production | Elevation / Tampering | restriction serveur (production seulement, pas de choix de version ancienne) ; `npm ci --ignore-scripts` ; la build de déploiement reste sous `sandbox-exec` avec `~/.config/rtp` illisible ; alerte Telegram à chaque activation (détection) ; journal serveur avec champ `auto` ; interrupteur et retrait documentés. **Risque résiduel accepté et écrit au RUNBOOK et dans l'ADR : la clé permet d'activer un envoi arbitraire** (la phrase de passe de la clé manuelle protège contre cela, c'est précisément ce que D-04 retire) |
| Ancien script serveur qui ignore `--auto` | Elevation | marqueur de capacité, ordre d'installation, sonde de restriction à chaque passage |
| Injection de prompt par le jeu data.gouv (`nom`, `statut_detail`, `propositions`, `source.titre`) ou par la page source | Tampering | agent sans outil ; données dans un bloc délimité et déclaré non fiable ; `statut_detail`, `propositions`, `bloc` jamais transmis (règle existante de `mapRow`) ; sortie réduite à un verdict, une citation vérifiée par code, une date ; deux agents indépendants ; écriture par code et gabarits ; pire cas : un mauvais verdict sur un statut que le jeu public affirme déjà |
| Texte libre de l'agent écrit dans le dépôt (neutralité, mots interdits, tirets) | Tampering | aucun champ libre n'est écrit ; garde de périmètre vérifie mots interdits et tirets sur les lignes ajoutées |
| Nom d'identité hostile (homonyme, caractère de contrôle, nom en majuscules, très long) | Tampering | règles de refus du point 4 ; identifiant contrôlé par `ID_CANDIDAT` |
| Fuite de secrets dans les journaux (jeton Telegram, jeton de l'agent, chemin de clé, hôte, utilisateur, adresse IP) | Information disclosure | `envDeBase()` plus le seul jeton pour `claude` ; `masquer` partout ; le prompt n'est jamais journalisé ; test de sentinelles |
| Aucune détection d'un push malveillant sur `main` par la clé de push | Tampering | clé de déploiement limitée à ce dépôt ; CI GitHub a posteriori ; alerte de publication |
| SSRF via les URL du jeu (adresse privée, redirection) | Information disclosure | `fetchSafe` (https, adresses publiques, redirections revérifiées, plafonds) |
| Déni de service : appels d'agent en boucle, coût | Denial | délai 5 min, `--max-budget-usd`, 6 personnes par passage, un seul passage à la fois (verrou), reprise au passage suivant seulement |
| Publication pendant un gel | Tampering | gels testés au début, avant le push et avant `activer` |
| Données d'une autre session publiées par erreur | Tampering | garde « version en ligne vs `main` » (`siteTouche`) avant d'ajouter le commit |

## Project Constraints (from CLAUDE.md)

- Astro statique, zéro JS par défaut, pas de framework serveur ; données YAML/JSON validées par JSON Schema, pas de BDD.
- Neutralité : mots interdits (« extrême », « populiste », « irresponsable », « courageux », « enfin »), étiquette revendiquée par le candidat, chiffrage du candidat seulement ; équité (même niveau de détail pour tous les candidats d'un thème publié).
- Sourçage : source primaire datée, copie archivée ; **ici** : aucun agent ne modifie `texte_source` ni `archives/**`.
- Vie privée : aucun cookie tiers, aucune donnée personnelle, aucun script externe.
- Dépendances : chaque dépendance ajoutée justifiée par écrit dans la PR (la phase n'en ajoute aucune).
- Secrets : aucun dans le dépôt ; GitHub Secrets et Vaultwarden ; clé automatique, jeton de l'agent et moyen de push dans `~/.config/rtp/` hors dépôt.
- Node 24 LTS via fnm ; tests `node:test` ; pas de tiret long ni moyen dans les textes français (hors des tirets simples).
- GSD : tout changement du dépôt passe par un workflow GSD ; la règle d'hygiène « code sur Git distant dans la première heure » s'applique aux livrables des plans.
- Instructions globales d'Erwan : critères de succès mesurables avant exécution (ici : les SC-1 à SC-4 et le tableau de validation), dogfooding (les règles de ce RUNBOOK s'appliquent à l'automate lui-même : logs structurés, retrait documenté, test de documentation).
